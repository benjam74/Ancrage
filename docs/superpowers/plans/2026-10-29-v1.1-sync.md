# v1.1 — Synchronisation : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Utiliser Ancrage sur plusieurs appareils sans perdre de données : fusion déterministe de deux bases, fusion par fichier (sans serveur), et synchronisation automatique optionnelle via Supabase.

**Architecture:** `src/core/merge.ts` fusionne deux instantanés (`Dump`) : union des historiques, dernière écriture gagnante pour notes, thèmes et réglages, pierres tombales pour les suppressions, réconciliation des cartes. `src/sync/` définit un `RemoteStore` (lire/écrire un instantané avec contrôle de version) et `syncOnce`. `src/sync/supabase.ts` implémente le `RemoteStore` et l'authentification par appels REST (`fetch`), sans SDK. L'interface ajoute « Fusionner une sauvegarde » et une section « Synchronisation » dans Réglages.

**Tech Stack:** inchangée (aucune dépendance ajoutée).

**Spec:** `docs/specs/2026-10-28-ancrage-v1-design.md` §3 (invariants de sync : union des logs, dernière écriture gagnante), §9 (sync v1.1).

## Global Constraints

- Fusion commutative, idempotente : `merge(a, b)` ≡ `merge(b, a)` et `merge(a, a)` ≡ `a` (à l'ordre près, tables triées par id).
- Historique (`reviews`) et manches (`events`) : union par id. Rien ne se perd.
- Notes et thèmes : la version au plus grand `updatedAt` gagne ; égalité départagée par comparaison du JSON (déterministe).
- Suppression : pierre tombale `{ id, kind: 'note' | 'theme', ts }`. Elle l'emporte sur toute version de date `≤ ts` ; une modification postérieure fait revivre l'élément.
- Cartes : réconciliées après fusion depuis les champs de la note gagnante ; deux cartes de même `(noteId, variant)` sont fusionnées sur le plus petit id, leurs révisions rattachées à celle-ci.
- Réglages : dernière modification gagnante (`settingsUpdatedAt`).
- Sauvegarde : format version 2 (ajoute `tombstones`, `settingsUpdatedAt`) ; la version 1 reste lisible.
- Supabase : une ligne par utilisateur (`ancrage_snapshots`), protégée par RLS ; écriture conditionnelle sur `version` ; 3 tentatives en cas de conflit.
- Connexion Supabase par e-mail et mot de passe ; jetons stockés localement, renouvelés automatiquement.
- La synchronisation automatique se lance à l'ouverture, après chaque manche et sur demande. Hors ligne, elle échoue sans gêner l'usage.

## Review Focus

1. **Même note modifiée sur deux appareils hors ligne** : la plus récente gagne partout, l'historique des deux appareils est conservé. → test Task 2.
2. **Note supprimée sur A, révisée sur B** : la note reste supprimée (la révision ne modifie pas la note) ; les révisions de B sur ses cartes disparaissent avec elle. → test Task 2.
3. **Même trou ajouté sur deux appareils** (deux cartes pour une variante) : une seule carte après fusion, les deux historiques rattachés. → test Task 2.
4. **Deux appareils qui synchronisent en même temps** : aucune écriture n'écrase l'autre (conflit de version → nouvelle fusion). → test Task 4.
5. **Jeton expiré, réseau coupé, mauvais mot de passe** : message clair en français, aucune donnée locale touchée. → tests Task 5.

### Task 4: Moteur de synchronisation

**Files:** Create `src/sync/remote.ts`, `src/sync/sync.ts`, `src/sync/memory-remote.ts` · Test `tests/sync/sync.test.ts`

**Interfaces:**
- `interface RemoteStore { get(): Promise<{ dump: Dump; version: number } | null>; put(dump: Dump, expected: number | null): Promise<{ ok: true; version: number } | { ok: false; conflict: true }> }`
