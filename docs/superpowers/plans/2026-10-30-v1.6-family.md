# v1.6 — Profils familiaux et domaines : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plusieurs profils par appareil (une base chacun) et des domaines au-dessus des thèmes, avec des cartes de départ « Collège 5e ».

**Architecture:** Registre des profils en `localStorage` (`src/app/profiles.ts`), stockage préfixé par profil, base Dexie par profil ; domaines = thèmes `kind: 'domain'` (`src/core/domains.ts`, pur) ; migration idempotente au démarrage.

**Tech Stack:** inchangée.

**Spec:** `docs/specs/2026-10-30-v1.6-family-design.md`.

## Global Constraints

- Profil existant : id `principal`, base `ancrage`, clés inchangées. Autres : base `ancrage-<id>`, clés `ancrage.p.<id>.<reste>`.
- Clés de registre (non préfixées) : `ancrage.profiles` ; choix de l'onglet : `sessionStorage` `ancrage.profileChosen`.
- Domaine par défaut créé par la migration : id `dom-principal`, nom « Coaching et PNL ».
- Code : exactement 4 chiffres, facultatif.
- Deux niveaux : un domaine n'a pas de parent ; un thème a un domaine pour parent (ou aucun, rangé « Sans domaine »).

## Review Focus

1. **Le parent rouvre l'appli après la mise à jour** : même base, mêmes cartes, série, boutique ; ses thèmes sont dans « Coaching et PNL ». → test Task 2 + e2e.
2. **Deux appareils migrent chacun de leur côté** : un seul domaine après fusion. → test Task 2.
3. **Registre corrompu** : retour au seul profil principal, rien n'est effacé. → test Task 1.
4. **Un enfant joue une manche** : l'XP et la série du parent ne bougent pas. → e2e Task 5.
5. **Thème déplacé vers un autre domaine sur un appareil, renommé sur un autre** : la dernière modification gagne (comme aujourd'hui). → test Task 2.
